# GlacierOS混合内核架构

## 内核架构定位
- 混合内核——介于宏内核和微内核之间
- FI芯片适配，独立于x86/ARM架构
- 经典设备专用——不考虑量子计算设备
- 主版本用人类C++23标准编写（也有C++59/60/61版本的内核，但几乎无碳基开发者使用）
- 部分核心代码禁止使用C++，必须用纯C编写——审计层级的要求

## 混合边界原则
- **稳定成熟的放内核态，不稳定多样的放用户态。** 文件系统和网络协议栈是岩石，设备驱动是屎山。
- **延迟敏感、可能会造成碳基生命生命危险的少数驱动放内核态，其余全放用户态。**

## 内核态（特权态——始终加载）

### Core\
- CPU调度：完全公平的实时调度——普通进程用完全公平调度，关键系统进程用固定优先级实时调度
- 内存管理：FI双层页表，虚拟地址空间隔离
- FI微码和基础系统调用

### IPC\
- IPC通道：进程间通信的唯一骨架——寄存器传参、固定长度消息、零拷贝传递大数据页
- SRM（安全引用监视器）：嵌在IPC层——原子令牌校验，不可绕过。每一条跨进程消息经过内核时，发送方的权限令牌组与目标对象的安全描述符当场比对——放行或拒绝

### Communication\
- ZP/ETE/ST协议栈内核实现
- 稳定成熟、高频通信、南极全网基础设施——放在内核态，不承受IPC延迟

### GFS\
- 文件系统内核实现
- 稳定成熟、高频读写、不能承受用户态IPC延迟
- 去重引擎在内核态运行

### HAL\
- FI芯片硬件抽象层
- 适配FI芯片三个变体：嵌入版（单核/无MMU/低功耗）、桌面版（多核/完整MMU/中等功耗）、服务器版（多核阵列/海量内存/高功耗调度）
- 职能：启动/关闭CPU核心、中断路由、读取时间戳、内存屏障和缓存一致性、页表配置
- HAL和用户态驱动之间没有特殊绑定关系——它是纯FI芯片适配层
- 代码量可能只有几千行——单一架构三个变体，编译器在构建时直接选定对应分支，无运行时性能损失

### Kernel\Drivers\
- 延迟敏感、可能会造成碳基生命生命危险的实时驱动（必须注册才能进入内核态）
- BrainInterface\：脑机接口神经编码——延迟超过10ms等于公民残障
- ServoControl\：R系列伺服电机实时控制——脉冲延迟累积导致机器人摔倒
- AntiGravity\：反重力装置磁场安全边界——反应慢一帧可能砸穿数据中心

## 驱动注册流程

### 默认：所有驱动在用户态
- 驱动开发完毕，`.kml`文件放在`Drivers\User\`下面
- 默认以用户态进程运行——崩了重启，不伤内核

### 注册进内核态（Glacier One OS 2.12.3起）

**热加载流程（当前标准）：**
1. 驱动持有 `SeKernelDriverRegisterToken` 令牌（不在Administrator默认令牌组，需单独申请+UAC弹窗+记入Logs）
2. 调用 `PromoteToKernel()` API
3. 内核暂停驱动进程的消息队列——新请求排队，已完成的请求正常返回
4. 内核验证令牌→校验驱动源码完整性→通过
5. 内核将驱动代码映射进内核地址空间，HAL更新中断路由表指向内核态实例
6. 旧用户态进程安全回收——所有状态（打开的文件句柄、分配的内存、持有的令牌）迁移至内核态
7. API返回HANDLE（CallToken），新请求开始流向内核态实例
8. 驱动文件无需移动——安全边界从文件系统收回到内核API

**热加载期间：** 请求排队，不丢失数据。校验失败→内核退回，用户态实例继续运行。脑机接口和伺服电机等实时驱动不建议走热加载——应直接调用 `InstallKernelDriver()`（见旧API）。

**旧API（Glacier One OS 2.12.8起废弃，保留但不推荐）：**
1. 调用 `InstallKernelDriver()` API
2. 内核把`.kml`文件移动到`Kernel\Drivers\`下面
3. 内核从新位置重新加载驱动
4. 需要重启驱动进程——不适合实时场景

**兼容性说明：** `InstallKernelDriver()` 在 2.12.8 后标记为废弃，但未被删除——依赖旧API的现有驱动继续工作。新开发一律建议使用 `PromoteToKernel()`。

### 安全边界（2.12.3起）
- 安全边界不在文件路径——在内核API
- 内核不关心`.kml`在哪个盘哪个目录，只关心调用者有没有令牌、驱动有没有通过完整性校验

## 用户态

### Foundation\
- C++标准库（四个标准的四个版本）
- FI硬件抽象
- 基础类型定义
- 纯用户态，崩了不影响内核

### Interfaces\
- 内核暴露给用户态的系统调用封装库
- IPC\：IPC客户端封装
- Security\：安全描述符API、ACL管理
- Communication\：ZP/ETE/ST的应用程序调用接口
- TokenRegistry\：令牌注册表查询和管理接口
- GFS\：文件系统调用接口

### Drivers\User\
- 所有用户态设备驱动（海量、多变、崩了重启不伤内核）
- GUI、GPU、音频、打印机、存储控制器、网络优化驱动
- 通过`Interfaces\`下的系统调用接口与内核通信

## 三种典型部署

| | Core+IPC+HAL | Communication | GFS | Kernel\Drivers | 用户态驱动 | 典型设备 |
|---|---|---|---|---|---|---|
| **微型嵌入** | ✓ | ✗ | ✗ | ✓ | 极简 | R-01机器人、脑机接口芯片 |
| **桌面** | ✓ | ✓ | ✓ | ✓ | GUI+GPU+音频 | 帝企鹅办公机、雄关日报 |
| **服务器** | ✓ | ✓ | ✓ | ✗ | 存储控制器+网络优化 | 超级路由器、聚变电站、数据中心 |

**说明：**
- 始终加载：Core + IPC + HAL——任何设备上都必须在内核态
- 编译时可选：Communication、GFS——桌面和服务器要，微型嵌入式不要
- 微型嵌入式不加Communication（R-01不需要ZP全网路由，最多局部组网），不加GFS（用FI内存映射替代）
- 服务器不加`Kernel\Drivers\`（不需要控制机械臂）
- 所有设备驱动默认在用户态，只有持有令牌且通过注册流程的少数实时驱动进内核态
